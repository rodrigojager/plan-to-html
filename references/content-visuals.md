# Choosing explanatory visuals

Use the source structure and the reader's question to choose a visual. The purpose is to make a comparison, sequence, relationship, or behavior easier to understand. An ordinary paragraph or small table may already do that well.

## Decision process

1. Start with the compact outline. Look for numeric tables, ordered stages, conditions, dependencies, alternatives, interface references, or explicit rules. Read only the relevant source sections.
2. State the reading need in one factual sentence, such as "Compare the latency of the three options" or "Identify which branch handles a failed payment". If the addition only makes the page look fuller, omit it.
3. Check that the source supplies the necessary facts. Counts of tasks, headings, or documents do not establish effort, implementation progress, acceptance, importance, or estimated duration.
4. Choose the simplest representation that answers the reading need. A visual can often replace the need for an *added explanation*; keep the source itself available, including the original table or prose. Do not generate several equivalent views of the same facts.
5. Implement useful additions within the authorized task. Do not ask the user to choose every chart. If a worthwhile addition needs missing data, mention the required data briefly in the handoff instead of fabricating it. There is no required number of visuals.

## Examples and selection criteria

| Source content and reading need | When to add a visual | Possible visual form | Evidence and implementation |
| --- | --- | --- | --- |
| Numeric comparison table: costs, latency, capacity, or counts | Several values share a measure and the reader needs to see their relative magnitude. | Horizontal bars with category labels, exact values, and the unit. Preserve a meaningful source order; use a zero baseline for magnitude comparisons. | Use `table-chart` to read the original cells. A table of text, IDs, mixed units, or one isolated value usually needs no chart. Do not combine unrelated quantities into one scale. |
| Measurements over dates or an explicitly ordered numeric axis | The trend or change matters more than looking up individual values. | A simple line chart, with the true intervals on the horizontal axis and the unit on the vertical axis. Show a few meaningful labels rather than labeling every point. | Requires actual observations and an ordered axis. A line between unordered categories implies a relationship the source does not establish. The built-in chart is bars; a line chart needs a small custom SVG/JavaScript extension with data extracted deterministically. |
| Stages, milestones, or a reading sequence | The reader needs to understand order, without many branches. | A compact numbered timeline; short labels link to the detailed sections. Use equal spacing for ordinal steps, and dated positioning only when the dates are supplied. | Use `timeline`. Keep descriptions to the one fact that distinguishes a stage. A simple list of three obvious actions may already be sufficient. Never infer duration from the length of a stage's description. |
| Conditional process, validation, retries, or alternate outcomes | Following the prose requires remembering which condition leads to which action. | A Mermaid flowchart with action rectangles, decision diamonds, and labeled branches. Use a vertical flow when horizontal labels become cramped. | Every branch and return path must come from the source. Do not add failure paths just because they are plausible. Prefer a numbered timeline when there are no meaningful branches. |
| Modules, services, responsibilities, and dependencies | The source establishes boundaries or data flow that are difficult to reconstruct from several paragraphs. | A small architecture diagram: group components by actual boundary; label arrows with the data, operation, or dependency. Use a separate view for a distinct level of detail when needed. | Use a Mermaid flowchart or a focused custom SVG. A Markdown hyperlink establishes a document connection, not an architectural dependency. Avoid diagrams that turn every noun into a node. |
| Requests, callbacks, events, or handoffs between actors | Who initiates each interaction and in what order is important. | A Mermaid sequence diagram with one lifeline per actor and concise message labels. Add an alternate branch only for a documented scenario. | Requires explicit participants and interactions. A static architecture diagram cannot establish event ordering by itself. For lifecycle states, a Mermaid state diagram may be more appropriate than a sequence diagram. |
| Alternatives with trade-offs, constraints, or eligibility rules | The reader needs to compare options across the same criteria. | Preserve the comparison matrix; use a small, labeled highlight for a confirmed decision or a source-backed constraint. If a quantitative criterion matters, chart that criterion separately. | Keep the original cells. Do not invent scores, rankings, a winner, or a recommendation. A categorical comparison does not become clearer merely by converting it to bars or a pie chart. Extra highlighting needs a scoped CSS/JavaScript extension, not a fabricated component type. |
| Screens, interface references, spatial descriptions, or interactions | The reader needs to connect a requirement to a visible area or behavior. | An existing screenshot or wireframe with a few numbered annotations, each pointing to the source requirement; a compact screen-flow diagram for navigation. | Use `image` for an existing reference and Mermaid for an established screen flow. Annotation overlays or a generated wireframe are custom additions. Distinguish a proposed mockup from an existing or approved interface, and reuse supplied references before inventing replacements. |
| A documented change with both current and proposed behavior | The benefit or effect of the change is easier to see side by side. | Two aligned panels labeled "Current" and "Proposed", using the same example, scale, and criteria; optionally a small diagram of each flow. | Both states must be established by the source. Do not manufacture shortcomings in the current state. Use focused Mermaid diagrams or custom SVG/HTML; retain the detailed source explanation. |
| A formula, decision rule, state machine, or bounded scenario | A reader would learn more by changing an input and observing its consequence than by reading another example. | A small interactive example with labeled inputs, the computed output, and a concise indication of the rule being applied. | Generate only when the rule and valid input range are explicit. Use deterministic JavaScript and local data; cite the formula or rule. Mark assumed inputs as examples, and do not present the simulation as measured or implemented project behavior. |

## Applying the guide

- Existing components are `mermaid`, `table-chart` (bars), `timeline`, and `image`. Use the schema in [enhancements.md](enhancements.md). Diagram variants such as flowcharts, sequences, and states go inside `type: "mermaid"`; do not invent component types such as `flowchart`, `line-chart`, or `simulator`.
- For a justified addition outside those components, use a separate CSS/JavaScript/SVG resource in the editable build, then run the final packager. Extract data from the parser or source table through code; do not copy a large data table into model-written JSON or JavaScript.
- Place a visual near the section it explains using `after`, rather than collecting every detail above the plan. Use `overview` for a genuinely useful cross-document orientation view. Cite the exact source sections.
- Name the subject directly: "Request flow", "Latency by option", "Delivery stages". Keep labels and explanations factual and concise. Do not add a slogan, introduction, or praise for the visual itself.
- Readability is a selection test: labels must fit, arrows must have an unambiguous meaning, units must be visible, and color must not carry meaning alone. Check light/dark, a narrow viewport, and keyboard access for interactive content. If simplification cannot make the visual readable, keep the source representation or split the explanation by topic.
