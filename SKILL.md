# plan-to-html

Create a beautiful, usable reading experience from an existing plan. Markdown remains the source of truth and the efficient handoff format for agents. Use the bundled renderer for conversion and styling; spend generation tokens on small visual additions that actually improve comprehension.

## Editorial rules

- Preserve the plan's original title and section headings. Do not rename the document to make it sound appealing.
- Never add slogans, taglines, promotional introductions, aspirational claims, rhetorical hooks, or generic praise. This includes copy such as "A new way to explore plans", "From context to detail", and "An experience designed for you". The prohibition applies to the HTML, diagrams, image captions, mockups, and other generated assets.
- Do not add a hero subtitle, welcome paragraph, teaser, or restatement of the introduction. The page starts with the source title and reading controls; the explanation stays in its source section.
- Added text must serve a specific reading need: identify a diagram, explain a relationship, name an axis, clarify a unit, describe an image, or operate a control. Keep it concise, concrete, and grounded in the source. Omit text that only decorates the page or says how good the interface is.
- Visual titles should name their subject directly, such as "Conversion flow", "Dependencies", or "Duration by stage". Prefer the source section title when it already identifies the subject. Use short factual sentences for explanations; visual polish comes from layout and interaction.
- Preserve the user's source prose even when its style differs. These rules govern text added by this skill; rewriting the plan requires a separate user instruction.

## Workflow

Resolve this skill's own directory as `SKILL_DIR`; commands below use paths relative to it. Requires Python 3.10+. If dependencies are absent, run `python "SKILL_DIR/scripts/setup.py"` once. The setup installs isolated dependencies, local reading/theme fonts and licenses, and a pinned Mermaid browser bundle; subsequent builds work offline.

1. Identify the input the user named: a plan directory, `PLAN.md`, or an explicit list of Markdown files. With a directory or `PLAN.md`, follow Markdown links in reading order and include remaining Markdown children inside that plan directory. Never sweep the entire repository for unrelated documents. Pass `--assets` only for additional reference folders belonging to the plan.
2. Run `python "SKILL_DIR/scripts/plan_html.py" scan INPUT --output outline.json`. Read this compact outline instead of all source files: document titles, heading references, brief excerpts, table dimensions, image references, task counts, and actual links. Read only the particular source sections needed to understand or design a visual. Use the host's workspace retrieval rules for those follow-ups.
3. Build immediately with `python "SKILL_DIR/scripts/plan_html.py" build INPUT --output work/plan.html`. The default build creates editable HTML with separate CSS, JavaScript, and image resources. This already provides the reader, document map, gallery, search, section-link copy and navigation highlight, source links, code highlighting/line numbers/wrap/copy controls, sticky table headers and first column, image zoom and intrinsic dimensions, diagram zoom/pan/fit/expanded view, saved reading size/spacing/width, reading position, print layout, and light/dark switch. Fonts are local, transitions respect reduced motion, and these features are deterministic. No model-written HTML is needed for the base experience. If a theme is requested, read [references/themes.md](references/themes.md), select a CSS file from `themes/` with `--theme NAME` (or pass its path), and keep the reader's structural CSS and JavaScript independent of it.
4. Read [references/content-visuals.md](references/content-visuals.md) to choose additions from the actual content: it gives examples of when a chart, timeline, flowchart, architecture diagram, annotated reference, or interactive example improves understanding, how it can look, and when to omit it. Implement the justified choices; the guide is not a checklist to fill. Author a **small** `enhancements.json`, following [references/enhancements.md](references/enhancements.md), and rebuild with `--enhancements enhancements.json`. Prefer selecting an existing table for a chart instead of repeating its numbers. Existing Mermaid fences are rendered automatically. Do not invent dependencies, dates, estimates, status, percentages, or claims. Every added visual cites the source sections it explains. The automatic document map depicts Markdown links, not implementation architecture.
5. Refine the editable output as needed, including custom CSS, JavaScript, animations, and interactions. These may differ substantially between plans. Keep the Markdown body generated by the renderer; author only the additional visuals and behavior. Preserve light/dark support and the editorial rules above.
6. **Package last:** run `python "SKILL_DIR/scripts/bundle_html.py" work/plan.html --output plan.html`. This independent step reads the actual final HTML and its resource references; it does not assume a particular stylesheet, script, template, or design. It incorporates local resources deterministically without rewriting the content. Keep the editable version for later changes. Read [references/packaging.md](references/packaging.md) when using module imports, CSS assets, or other nontrivial dependencies.
7. Inspect the final packaged file in a browser when available, from its new location with network requests blocked. Check light/dark, narrow viewport, navigation, search, images, custom interactions, and diagrams. Otherwise report that visual inspection was unavailable. Use `.manifest.json` for source coverage and `.bundle.json` for incorporated resources; do not read generated HTML or encoded resources into model context.
8. Deliver the standalone HTML and mention unresolved dependencies. If useful, give the rebuild/package commands. Preserve the input Markdown and editable resources.

## Design and output

- The bundled visual system provides clear hierarchy, readable content widths, consistent controls, and generous spacing. Its default is restrained; reusable themes also provide neon, handwritten, crayon, parchment, newspaper, modern, minimal, maximal, Art Deco, and terminal appearances. Honor the requested visual style while preserving legibility and concise factual copy. Select appearance before generation with `--theme NAME|CSS_PATH` and `--accent mint|blue|amber|rose`. Themes use documented variables and inherit missing defaults. Users can download a compatible CSS into `themes/` without modifying Python, JavaScript, or templates. Do not regenerate the baseline styles per task or model. Use [references/themes.md](references/themes.md) for the contract and file organization. The theme comparison selector belongs only to the example preview; never add it to ordinary output unless explicitly requested.
- Syntax highlighting uses only the code fence's declared language (Pygments); unknown languages stay plain. Line numbers are CSS content and never enter the copied code. Image dimensions come from local file metadata, with SVG viewBox and EXIF orientation support. Tables and diagrams retain the complete source content. No automatic control infers semantic stages, status, architecture, or chart suitability; those belong to the optional content guide.
- Light and dark modes are mandatory, with a visible switch, persisted preference, system default on first visit, and diagrams that follow the selected theme. Maintain keyboard navigation, visible focus, contrast, reduced motion, mobile navigation, accessible dialogs, and print output.
- Reading maps must isolate the focused document and its direct incoming/outgoing neighbors on hover or keyboard focus; unrelated cards become invisible while retaining their positions. The pin control preserves that neighborhood on click/touch, and Escape or "Show all" restores the overview. Dense maps show connections on demand. Use the bundled foreground, collision-checked routing through card gutters; never restore free curves that cross or disappear behind cards. Keep document-title links navigable and reciprocal directions visible. See [references/reading-map.md](references/reading-map.md) when changing graph behavior or verifying a dense map.
- Keep the complete source prose, lists, tables, code, footnotes, decisions, and reference links available in reading order. Do not paraphrase or prune the plan for presentation. Interpret Markdown through the parser, not regex substitutions over its body. Missing references appear in the report and in the reading experience instead of silently disappearing.
- Editable output uses separate resources by default. The final packaged file contains its CSS, JavaScript, local images (including SVG, PNG, and BMP), CSS image/font resources, and needed Mermaid library. It opens through `file://`. The packager stops on missing or external static resources rather than labeling an incomplete file self-contained. Remote resources must first be saved locally when authorized; `--allow-external` explicitly produces a file with reported external dependencies.
- Add custom CSS/JavaScript through `--extra-css` / `--extra-js`, an ES module through `--extra-module`, or resource references in the editable HTML. Use `planhtml:ready` / `planhtml:theme` events where appropriate. Keep generated source content intact. The packager consumes the final resources instead of restricting creativity to the bundled assets.
- For a direct standalone build, `--format single` invokes the same packaging step after rendering. Prefer the explicit two-stage workflow when developing custom visuals. External APIs and URLs constructed at runtime need an offline implementation; embedding the script does not replace a live service.
- Do not print full HTML, full Markdown, embedded images, or vendor bundles into tool output. The model does not need to read runtime assets to execute the renderer. A rebuild performs the adaptation without generation tokens; the enhancement specification is the only routinely authored presentation content.

## Commands

```text
python SKILL_DIR/scripts/setup.py
python SKILL_DIR/scripts/plan_html.py scan path/to/PLAN.md --output outline.json
python SKILL_DIR/scripts/plan_html.py build path/to/PLAN.md --output work/plan.html
python SKILL_DIR/scripts/plan_html.py build path/to/PLAN.md --output work/plan.html --theme slate
python SKILL_DIR/scripts/plan_html.py build path/to/plan --output work/plan.html --enhancements enhancements.json
python SKILL_DIR/scripts/bundle_html.py work/plan.html --output plan.html
python SKILL_DIR/scripts/plan_html.py build first.md second.md --output plan.html --explicit --format single
```

For the CLI's full options use `--help` or `build --help`. Reuse the same enhancement file when Markdown changes; a missing section reference is a build error so a visual cannot silently attach to the wrong content.
